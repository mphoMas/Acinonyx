## 1. Acceptance mapping overview

This matrix maps every remedy and diagnostic finding from the *Acinonyx Rework Case Study* and every delivery process gate rule (G01–G10) to a concrete GitHub Actions / MAS Coordinator control, its accountable component, a testable failure case, and the exact check method demonstrating failure.

Accountable components:
- `mas.pm.delivery.DeliveryService`: Server-side delivery gate logic and database schema.
- `mas.pm.coordinator.CoordinatorStore`: Durable execution, intents, runs, and reservations.
- `mas.pm.adapters.admission.EvidenceTrust`: Service-owned cryptographic evidence validation.
- `mas.pm.adapters.verifier`: Independent verification and review receipt generation.
- `gha.workflow`: GitHub Actions workflow definition on protected base ref.
- `gha.runner`: Runner bridge script and isolated container execution harness.

## 2. Comprehensive acceptance matrix

| Gate / Remedy | Case Study Diagnosis | Concrete GHA & Coordinator Control | Accountable Component | Testable Failure Case | Check Method Demonstrating Failure |
|---|---|---|---|---|---|
| **G01: Versioned brief & distinct actors** | Incomplete boundary closure; moving target; unassigned or mixed roles. | `DeliveryBrief` model validation requires exact base SHA, policy version, scope list, requirements, checks, and 4 pairwise distinct principals (coordinator, builder, verifier, reviewer). GHA verifies brief is in `READY` phase before executing. | `mas.pm.delivery.DeliveryService` / `gha.runner` | Attempting to dispatch GHA check with only 3 distinct actors, empty scope, or unagreed brief. | Pass brief where `builder == verifier` or `reviewer_agreed == 0`; assert `ValueError("Four distinct assigned principals required")` or `DeliveryGateError("Agreed, ready delivery brief required")`. |
| **G02: Additive positive & adverse checks** | Tests measured weaker properties; lack of negative/falsification checks; superficial passing. | Brief validation requires every requirement to have at least one positive check (`negative=False`) and at least one adverse check (`negative=True`). Critical tasks require non-empty `mechanism` explanation. | `mas.pm.delivery.DeliveryService` | Submitting a brief where a requirement only has a happy-path check and no adverse/falsification check. | Call `DeliveryService.establish()` with a requirement lacking a negative check; assert `ValueError("Each requirement needs positive and adverse-case checks")`. |
| **G02 (Runner): Immutable test oracle** | Candidates modified test assertions or test fixtures to pass checks artificially. | Two-checkout pattern: GHA checks out verification tests from trusted base ref, not candidate commit. Suite hash checked against `brief.suite_digest`. | `gha.workflow` / `gha.runner` | Candidate PR commit modifies a file in `tests/` or alters pytest assertions. | Runner computes test suite digest; if `digest != brief.suite_digest` or candidate modifies `tests/`, runner aborts with scope violation error. |
| **G03: Pre-spawn & intent linkage** | Concurrent integration races; untracked or orphaned executions; execution on stale brief. | `require_dispatch()` and `record_dispatch()` link intent to exact task and brief version within SQLite atomic transaction. Intent pre-spawn verifies version matches. | `mas.pm.delivery` / `CoordinatorStore` | Dispatching an intent against an issue whose policy version or path whitelist changed after brief establishment. | Mutate `pm_issues.policy_version` and attempt dispatch; assert `DeliveryGateError("Stale delivery brief or pending plan reconciliation")`. |
| **G04: Candidate-bound submission** | Execution success mistaken for process acceptance; candidate substitution. | `DeliveryService.submit()` verifies `run.candidate_commit_sha == submission.candidate_sha`, `run.status == SUCCEEDED`, and `run.exit_code == 0`. GHA binds exact candidate SHA. | `mas.pm.delivery.DeliveryService` | Submitting a candidate commit SHA that differs from the commit actually executed in the coordinator run. | Call `submit()` with mismatched `candidate_sha`; assert `DeliveryGateError("Submission is not bound to successful current execution")`. |
| **G04 (Screening): Readiness screening** | Broken candidates sent directly to reviewers, wasting human/senior review capacity. | Builder submits check observations. Any non-passing check or missing check produces `READINESS_RETURNED`. Candidate does NOT enter `IN_REVIEW`. | `mas.pm.delivery.DeliveryService` / `gha.runner` | Candidate fails 1 of 5 checks; builder submits observations. | Call `submit()` where one observation outcome is `FAILED` or `SKIPPED`; assert returned task phase is `READINESS_RETURNED`, not `IN_REVIEW`. Reviewer receipt admission is refused. |
| **G05: Justified blocking findings** | Reviewers introducing undisclosed new requirements as defects, or rejecting without reproduction. | `DeliveryService.reject()` requires explicit `Finding` objects citing an existing requirement in the brief, reproduction, impact, and closure paths. | `mas.pm.delivery.DeliveryService` | Reviewer attempts to reject with a finding referencing an unlisted requirement ID. | Call `reject()` with an unlisted `requirement_id`; assert `DeliveryGateError("New requirement must be recorded as scope change, not rejection")`. |
| **G05 (Scope): Explicit scope changes** | Optional improvements or new requirements silently becoming blockers. | New requirements must be submitted via `request_scope_change()`. Coordinator either establishes updated brief (incrementing version) or calls `decline_scope_change()`. | `mas.pm.delivery.DeliveryService` | Attempting to bypass a pending scope change request through ordinary `resume()`. | Call `request_scope_change()` then attempt `resume()`; assert `DeliveryGateError("Resolve pending scope proposal before correction resumes")`. |
| **G06: Related-path closure coverage** | Incomplete fixes closing only the symptom while leaving related paths open. | `Submission` must provide `closures: dict[str, list[str]]` mapping each open finding to its touched paths, which must cover all `closure_paths` specified in the finding. | `mas.pm.delivery.DeliveryService` | Builder submits a fix that addresses the finding but omits one of the required related paths from `closures`. | Call `submit()` with incomplete closure paths; assert outcome is `READINESS_RETURNED` with reason `"Incomplete related-path closure"`. |
| **G06 (Recurrence): Recurrence pause** | Repeated patch loops on the same failed invariant without addressing root cause. | If a reviewer rejects a requirement that was previously claimed closed in `closures`, phase becomes `RECURRENCE_PAUSED`. Reassessment required before new dispatch. | `mas.pm.delivery.DeliveryService` | Candidate resubmitted with fix for Req-A; reviewer rejects Req-A again under a new finding ID. | Call `reject()` on a requirement previously claimed closed; assert phase becomes `RECURRENCE_PAUSED` and `recurring=True` in event body. |
| **G06 (Reassessment): Mandatory design plan** | Blind retry of failing work without architectural reconsideration. | In `RECURRENCE_PAUSED`, dispatch is blocked. Only coordinator calling `resume(design_plan=...)` can return task to `READY`. | `mas.pm.delivery.DeliveryService` | Attempting to dispatch a new worker or GHA run while task is in `RECURRENCE_PAUSED`. | Call `require_dispatch()` while task is `RECURRENCE_PAUSED`; assert `DeliveryGateError("Agreed, ready delivery brief required")`. |
| **G07: Builder challenge of findings** | Reviewer errors or misinterpretations forcing unnecessary code rework. | Builder can call `challenge(finding_id, reason)`. Phase becomes `DISPUTED`. Coordinator resolves with `resolve_challenge(upheld=...)`. If overturned, `resume_review()` permits re-review without code retry. | `mas.pm.delivery.DeliveryService` | Coordinator attempts to resolve challenge without specifying `upheld` boolean or reason. | Call `resolve_challenge()` with invalid arguments; assert `DeliveryGateError("Explicit challenge disposition required")`. Verify prior challenge event remains in immutable ledger. |
| **G08: Independent verification receipts** | Self-approval by builders; forged passing labels in database. | `DeliveryService.accept()` validates distinct verification and review IDs using service-owned `EvidenceTrust`. Receipts must match run, candidate, base, policy, suite digest, and roles. | `mas.pm.delivery` / `EvidenceTrust` | Attempting to call `accept()` with verification and review receipts signed by the builder, or with mismatched candidate SHA. | Call `accept()` with builder-signed evidence; assert `PermissionError("Caller is not assigned verifier")` or `DeliveryGateError("Trusted evidence does not match delivery assignment")`. |
| **G08 (Authority): Premature DONE prevention** | Direct DB write or FSM transition to DONE before process acceptance. | `require_accepted()` hook in coordinator and PM store blocks transition to DONE unless `pm_delivery_tasks.phase == 'ACCEPTED'` and receipts are verified in same transaction. | `mas.pm.delivery` / `mas.pm.db` | Direct SQL or FSM call attempting to move issue to `DONE` while task is in `IN_REVIEW`. | Attempt PM issue close; assert `DeliveryGateError("Independent delivery acceptance required before DONE")`. |
| **G09: Append-only immutable ledger** | Evidence erasure; overwriting previous failed attempts; history lost across restarts. | SQLite triggers `pm_delivery_events_no_update`, `pm_delivery_events_no_delete`, `pm_delivery_submissions_no_update`, `pm_delivery_submissions_no_delete` abort mutations. | `mas.pm.delivery` (DDL triggers) | Direct SQL `UPDATE` or `DELETE` executed against `pm_delivery_submissions` or `pm_delivery_events`. | Execute `UPDATE pm_delivery_submissions SET outcome='IN_REVIEW' WHERE id=1`; assert `sqlite3.IntegrityError: Delivery submissions are immutable`. |
| **G09 (CAS): Competing stale decisions** | Race conditions between concurrent review comments or runner updates. | All state transitions require exact integer `revision` matching `pm_delivery_tasks.revision`. Mismatch fails with `Stale delivery revision`. | `mas.pm.delivery.DeliveryService` | Two concurrent runners attempt to submit against revision 3 simultaneously. | First call succeeds and increments revision to 4; second call with revision 3 fails with `DeliveryGateError("Stale delivery revision")`. |
| **G10: Uncertainty & funding holds** | Runner crashes or cancellations releasing budget holds prematurely or retrying uncontained jobs. | Interrupted or cancelled runs record `UNCERTAIN`. Funding holds remain `HELD`. Gate refuses new dispatch until `reconcile_execution()` is called. | `mas.pm.delivery` / `CoordinatorStore` | Attempting to establish a new brief or dispatch an issue while a previous intent is in `UNKNOWN_EXECUTION` or reservation is `HELD`. | Call `establish()` or `reconcile_execution()` while reservation is `HELD`; assert `DeliveryGateError("Resolve existing funding holds before enrollment")` or `("Funding hold remains unresolved")`. |
| **Case Study: Boundary isolation** | Container escaping to host files, Docker socket, or credentials. | GHA runner container executed with `--read-only`, `--network=none`, `--cap-drop=ALL`, rootless user, and no Docker socket mounted. | `gha.runner` | Candidate execution attempts to access host `/var/run/docker.sock` or environment secrets. | Run adversarial test inside runner container attempting to open Docker socket; assert `FileNotFoundError` or `PermissionDenied`. |
| **Case Study: Status invalidation** | Stale passing check status remaining green after author pushes new broken commit. | GitHub Check Runs are strictly bound to `head_sha`. Push of new commit invalidates previous status; merge blocked until new commit passes. | `gha.workflow` / GitHub Branch Protection | Pushing commit B to PR while commit A had passing Check Run. | Inspect PR mergeability: PR remains blocked on `mas/delivery/acceptance` check for commit B until commit B completes gate. |
| **Case Study: Repeat work metrics** | Repeat work hidden in chat relays and untracked PR revisions. | `DeliveryService.metrics(issue_id)` aggregates counts of returns, rejections, pauses, challenges, and overturned findings from immutable ledger. | `mas.pm.delivery.DeliveryService` | Candidate goes through 2 readiness returns and 1 recurrence pause before acceptance. | Call `DeliveryService.metrics(issue_id)`; assert `readiness_returns == 2`, `recurrence_pauses == 1`, `acceptances == 1`. |

## 3. Verification method summary

1. **Unit tests (`tests/test_delivery_process_gates.py`)**: 47 automated tests verifying database transactions, DDL triggers, role boundaries, CAS revisions, readiness screening, recurrence pausing, and challenge resolutions.
2. **Integration tests (`tests/test_gha_delivery_integration.py`)**: Proposed test suite to verify GHA runner bridge, token authentication, check observation parsing, artifact digest verification, and stale commit rejection.
3. **Runner container qualification**: Docker container boundary qualification verifying zero network, read-only rootfs, and no Docker socket exposure.
4. **End-to-end rehearsal**: Synthetic task lifecycle executing through initial draft, readiness return, corrected submission, reviewer rejection with recurrence pause, coordinator reassessment, and final independent acceptance.
